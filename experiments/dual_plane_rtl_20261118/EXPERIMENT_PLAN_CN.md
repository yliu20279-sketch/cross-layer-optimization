# 双平面 NoC 实验计划与分工（2026-11-18）

建议刘宇晨负责硬件对照、连线核查和实现代价；我负责统一流量回放、算法时序、收益归因和论文结果整理。先补齐能否成立的证据，再扩展主表，避免两个人重复跑同一批实验。

## 1. 当前基础与待回答的问题

主线保持为：**一个 MoE 任务与一个通算事务流混合运行**。GetS/DataS 按包类型走新增 C Mesh，MoE 使用原 M Mesh 和 CS。不再引入双 MoE 场景。

已完成 312 组 RTL 回放、1,872 个通信阶段，包括共享 Mesh、双平面关闭 CS、在线控制原型、强制 CS、HiBand 三种通道分配、两类单跑及相同配置等待的 Mesh 对照。包、数据、网络字节与 SRAM 服务次数审计通过。规模是 4/8/16 token，拓扑固定为 4×4。

当前结果说明：

- 双平面关闭 CS，相对 HiBand 适配版逐阶段理想最优模式的阶段总时间，几何平均加速比为 **1.0237**；30 个算例中 20 个缩短、10 个持平。
- 强制 CS 相对关闭 CS，几何平均加速比为 **0.9922**；相对相同配置等待的 Mesh 对照为 **1.0052**。旁路有作用，但配置与等待成本可以抵消它。
- 在线原型计入主机墙钟耗时后没有提交更新。它从通信阶段开始规划，使用精确 RTL 回放判断时序；没有实现前一计算层中的提前规划，不能据此认定论文算法已经获得在线收益。
- 当前 GetS 是合成只读事务，结果是通信阶段时间，尚不是完整 CPU 程序或数值 MoE 推理时间。结构综合已记录退出码 137，尚未完成结构验收；面积、时序和布线代价也未验收，采集状态见 `evidence/SYNTHESIS_SNAPSHOT.json`。

下一轮优先回答三个问题：

1. **在 NI 和路由器都采用按类型优先服务之后，混合干扰还剩多少？新增 C 平面的收益是否仍值得其实现代价？**
2. **CS 能否在计入规划、排空、配置与确认后，稳定优于不更新配置？**
3. **当前拓扑与端口连线能否按统一工具、工艺库和时钟约束实现？**

## 2. 共同实验约定

| 项目 | 固定口径 |
|---|---|
| 拓扑与分类 | 4×4 M Mesh、4×4 C Mesh，NI 一一对应；原 9+4 个 CS。GetS/DataS 按类型进入 C，MoE 控制包不因尺寸小而进入 C。 |
| 数据格式 | 256 bit 数据 flit；32 B 包头；MoE 每包最多 512 B 载荷；GetS 请求 32 B，DataS 为 32 B 包头加 64 B 数据。 |
| 流量规模 | 每阶段匹配两类流量的网络字节数，请求和响应都计入；Bank 内部读不重复算作网络字节。 |
| 队列 | 普通路由器和 NI 每个有效虚拟网络的队列深度为 2 flit；HiBand 串并转换缓冲单列，不能隐去。 |
| 共同端点 | NI 总发送、总接收及共享 SRAM 服务参数保持一致；默认 Bank 等待 8 周期，每源最多 16 笔未完成 GetS。改变参数必须单列。 |
| 到达规则 | 同一算例的源、目的、就绪规则和数据一致。不把旧方案的完成时戳作为新方案的就绪时戳。 |
| 主要指标 | GetS 事务完成时间与 P99、MoE 完成时间、阶段汇合时间；另记 NI 等待、实际配置周期和规划耗时。P99 按阶段计算，不能混称全应用 P99。 |
| HiBand | 使用已声明的 NoC 适配版，分别记录 4/0、2/2、1/3 分配；逐阶段免费选择最快模式只作为乐观边界，不作为已实现在线策略。 |
| 成本 | 新增 C 平面不是等面积变化；必须同时报告收益、寄存器/面积、频率和连线代价。 |

共同 GitHub 入口为 `codex/dual-plane-noc-design-20261117` 分支的 `experiments/dual_plane_rtl_20261118/`。本计划、归因对照脚本与 312 组回执随本次提交一并归档；双方以本次上传的同一提交开始，并用 `git rev-parse HEAD` 登记版本。090a55d 是之前的源码入口，当前完整共同基准以包含本计划和 `PACKAGE_MANIFEST.json` 的提交为准。

## 3. 刘宇晨负责

### L1：核对 HiBand 适配与物理连接

先核对论文 Fig. 6 及相关设计部分，交付一张“论文机制—当前实现—平台映射假设”表。重点包括：

- global/local 是否确实共用四条物理通道；192 bit 分配是否连续打包，而不是每个 flit 向上取整。
- NA 划分、本地直达条件和全局路径是否符合所声明的平台映射。
- Beneš 的有效端口、未用端口及路由配置是否匹配，不能只保留通道配额而省略交换数据通路。
- CS 与 NI 的宽数据连接是否只使用拓扑中真实相连的端口。特别核对 CS 到 NI 的输出选择，避免综合出图中没有的宽交叉连接。
- 配置只能在排空后提交；源 NI 版本、数据包完整性和失败后的状态保持正确。

发现差异时先记录影响范围并修正，不把未经核实的映射写成作者实现。修改后运行共同回归，再提交硬件版本。

### L2：实现按类型优先服务的对照

保留现有 RR，新增可选择的类型优先策略。该对照只改变 NI 发送/接收与路由器的仲裁，不增加链路、队列、缓存或端点带宽。请求与响应仍有独立虚拟网络，配置消息仍能完成；共享 SRAM 仲裁先保持原样。

建议配置消息优先，其次 DataS、GetS，最后 MoE；同类型内部保持现有轮询与包内顺序。分类依据是包类型，不是包长。明确实现顺序并固定，不能逐算例换规则。

先跑下面 6 个开发算例：16 token、seed 641103，热点/分散请求 × 间隔 1/3/6 周期。新增四个对照臂：

1. 共享 Mesh，类型优先。
2. HiBand 适配版，类型优先，分别采用三种通道分配。

即 **6×4=24 组预检**，已有 RR 结果用于配对。交付代码、构建回执和逐阶段结果。我负责与现有结果统一审计；预检通过后再扩展到全部 30 个算例。

判定时同时看 GetS 与 MoE。若优先服务以很小的 MoE 代价消除了主要等待，就应重新评价新增平面的必要性；不能仅凭新平面优于 RR 就宣布问题成立。

### L3：统一硬件代价评估

使用同一套可用工具、工艺库、顶层边界和时钟约束，比较：

| 硬件版本 | 用途 |
|---|---|
| 共享 Mesh + NI | 基础成本 |
| M+C 双平面 + NI，硬件移除 CS | 分离新增平面的成本 |
| M+C+CS 完整方案 | 完整硬件成本 |
| HiBand NoC 适配版 + NI | 对照硬件成本 |

“运行时没有启用 CS”不能当成“综合时没有 CS 硬件”。共同端点 SRAM、计算核与 DMA 是否计入必须一致；调试计数器、配置控制器及被移除的逻辑要列清楚。

交付面积或资源数、寄存器位数、关键路径、目标时钟下的时序结果，以及物理链路与 NI 连接数量。若只有通用逻辑综合，明确它不等于标准单元面积或布局布线结果。1 ns 目前只是仿真参数，不能先认定硬件达到 1 GHz。若为满足时序增加流水级或改变服务周期，必须重新回放，并按共同可实现时钟核对实际时间。

## 4. 我负责

### C1：统一基准、回放和归因

整理现有 312 组回执、脚本与源码哈希，保留单跑、关闭 CS、强制 CS、相同配置等待的 Mesh 对照。接入刘宇晨的类型优先版本，按同一输入重跑必要配对，分别回答：

- 哪些等待来自网络，哪些来自共享 NI、SRAM 或请求本身过载？
- 双平面改善的是事务尾延迟、MoE 进度，还是阶段总时间？
- CS 的效果能否超过相同配置等待但仍走 Mesh 的控制组？

### C2：修正在线算法的时间安排

把精确 RTL 回放留作离线验证，研究可在运行时执行的轻量时序估计。分别记录候选构造、估计、排空、配置和确认成本，区分主机墙钟与实际部署控制器的周期成本。

显式加入可用于提前规划的计算间隙，扫描从没有提前时间到能够完成决策的窗口，报告最小所需窗口。若没有应用中真实的计算间隙，就把它标为受控参数，不能挑一个有利数值当真实运行时间。

比较“不更新配置”和“完整在线算法”，检查 GetS 与 MoE 的完成时间及退化预算。若没有净收益，就保留回退结果，不能用强制 CS 或免费预配置代替在线算法主表。

### C3：依赖关系与留出验证

只有拿到独立计算时间与明确阶段依赖后，才推进多阶段依赖回放；已有旧完成时间不直接作为新阶段起点。结果按实际覆盖范围称为事务/通信阶段完成时间，不提前称作完整应用加速。

现有三个 16-token seed 都已经看过，不能再事后改称留出测试。算法调定后需要新生成的轨迹做确认。若刘宇晨方便，可在既有生成脚本上补两条新 seed 的 16-token 传输元数据，由我登记哈希并冻结；真实邻层预测若要进入主表，还需要同一 token 组的相邻层专家计数。没有这些标签时只报告已确认元数据下的实验。

### C4：整理论文证据

由我统一生成表格、动机图和文字，区分分流收益、CS 旁路收益与在线算法收益。实验完成后再填入摘要与主结论，不把局部回归、尾延迟下降或理想预配置直接写成完整性能结论。
